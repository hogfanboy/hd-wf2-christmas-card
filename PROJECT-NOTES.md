# Pocket Jumbotron: project notes (spec and settled truth)

What the product does, verified hardware facts, decisions and gotchas. Add only things that are built and verified.
Current work is in PROGRESS.md; untested ideas and the backlog are in IDEAS.md. Last updated 2026-11-20.

## What it is
Custom firmware + website for ~15 LED "Christmas cards" already mailed out last year. Each one is a Huidu **HD-WF2 V7.2** controller (ESP32-S3, 8 MB flash, **no PSRAM**) + one **P2.5 HUB75E 128x64, 1/32-scan** panel + a 5V 10A supply (barrel jack → WF2 screw terminals). Stock Huidu firmware only does 3-bit color. Our firmware gives 8-bit color, the user's own pictures, and wireless updates. The name is **Pocket Jumbotron** (not tied to one family's card).

- Repo: https://github.com/hogfanboy/hd-wf2-christmas-card (public). Website: GitHub Pages from `/docs` → https://hogfanboy.github.io/hd-wf2-christmas-card/
- **Never commit** the user's media (`media/`, many are commercial characters) or Huidu firmware dumps (`firmware-backup/`). Both are gitignored.

## Features (verified on the cards)
- **Show** (fw 0.7.0+, `show.ino`): `/show.txt` lists items (tab-separated): `pic`, `text` (fonts: 1 pixel, 2-4 classic small/medium/big, 8-12 Jumbo; the 0.9.4 slanted fonts 5-7 load as 2-4; color or rainbow, snow/sparkle background), `clock`, `countdown` (MM-DD + label), each with seconds (0 = auto). Without show.txt every picture in `/gifs` plays in name order. **Shuffle** (1.0.0-beta3): a line `order<TAB>shuffle` = random order, new every round, never the same item twice in a row (page: Play order In order / Shuffle; older firmware skips the line). **Schedule** (0.9.1): an optional last field `@dates=MMDD-MMDD days=0123456 hours=H-H lead=N forecast` limits when an item plays (`itemActive()`); `lead` makes a countdown a reminder (only the last N days). Items with a time rule wait for the clock. Auto timing: short animations loop for ≥8 s; long ones stop at ~20 s at the end of a loop.
- **Startup screen** (0.8.1): the arcade "POCKET JUMBOTRON" marquee from `firmware/intro.gif`, built into the firmware.
- **Effects + weather** (fw 0.8.0): `fx` items and effect backgrounds (snow, sparkle, hearts, confetti, fireworks, stars, fire, matrix; plasma removed in 0.8.1) drawn by the card; `weather` items fetch Open-Meteo over plain http (~150 ms, no TLS), at most every 15 min, 5-min back-off after a failed fetch; `forecast` adds a 5-day screen (0.9.1; on by default for new weather items in the page since 0.9.5). Ran for several loops on card 1 with no resets, heap steady ~81 KB. **1.0 effects** (`effects.ino`, sprites as letter rows shared with the page's `SPR`): `sleigh` (Santa + 2 reindeer, glitter trail; full screen under a twinkling sky, behind text along the top), `balloons`, `fish` (aquarium: fish both ways and bubbles on black, a background for text; water and seaweed removed in 1.0.0-beta5), `rain`, `lights` (1.0.0-beta7: a string of 44 2x2 bulbs, red/gold/green/blue, on a dim green wire around the edge; full screen it switches twinkle / chase / alternate blink every ~6 s over snow, behind text it only twinkles), and `auto` = "match the weather" (weather items only: snow or rain when the weather is, else none). One loop of all of them on card 1: no resets, heap ~79 KB.
- **Pictures**: `.gif` (AnimatedGIF, ≤256 colors/frame) or `.pjm` full color = `PJM1` + per frame [u32 len, u16 delay ms, u16 0, baseline JPEG], decoded with JPEGDEC 1.8.5 (RGB8888). The card page converts any input (JPG/PNG/GIF/WEBP/MP4/MOV/WEBM, animated WEBP split into frames by the page itself, because `ImageDecoder` exists only on https pages) and picks GIF or full color per picture (1.0.0-beta3: GIF when a 254-color palette copies the picture closely, RMS error ≤ 4.5 on up to 6 sampled frames, else full color; cartoons have 1000+ colors only from smoothing yet are near-perfect as GIF). Page GIFs store only changed pixels after the first frame (like `tools/gif-encode.mjs`). Full color = near-black (<16) to black, then a **4:4:4** JPEG (vendored jpeg-js encoder, quality 92): the browser's own JPEG halves color resolution and smeared reds/greens badly (RMS error 5-10 vs 2-3). The card also floors near-black after decoding. The preview shows the encoded result. Before scaling, a plain-color border (all four corners within 48 summed RGB of the top-left) is trimmed to the content box over up to 20 frames + 3% margin, when that box is under 80% of the picture (not for 128x64 frames read back from a screen); near-black (<16) is floored to black for GIF too (1.0.0-beta4). Conversion code lives in `web/convert.js` (shared with the pack builder). **Videos** (1.0, page only): a hidden `<video>` is seeked frame by frame, start + length chosen per clip (up to 30 s, 12 fps, ≤150 frames).
- **Time**: NTP after WiFi joins; POSIX TZ string worked out by the phone page from its own DST changes. Night mode: hours + brightness level (NVS).
- **Player**: **Single-buffered** (redraws only changed pixels), 8-bit color, brightness capped at 55% of full (`MAX_BRIGHTNESS` 140); the user's % setting is saved in NVS.
- **Home WiFi** (`net.ino`): the card joins the saved WiFi and serves the app at its IP (0.9.0: `/` is a tiny starter page that loads the app from the website, `docs/app/`, built by `tools/build-web.mjs` in CI, and keeps a copy on the phone; `/local` is the built-in copy) **and** at `http://pocketjumbo-XXXX.local` / `http://pocketjumbo-XXXX` (mDNS + DHCP hostname) while GIFs keep playing. Page: build the show, load the current show back (`GET /api/show`, `/api/file`; 0.9.5: automatically when the page opens, so adding one reminder can't wipe the rest on Send), only one item open for editing (the rest are compact tap-to-open rows, ✕ top right removes), Send (= replace everything), packs, brightness, clock/night settings, one-tap update from `info.json` on the website, firmware file upload, forget WiFi. Browser tab icon: `docs/favicon.svg` on the website; the card's pages, install.html and the pack builder carry the same SVG inline (data: URI).
- **Improv WiFi over USB** (fw 0.9.8, fixed + "WiFi only" in 1.0.0-beta5): `net.ino improvPoll()` (called from netService) speaks Improv Serial (improv-wifi.com) on the USB serial port next to the log: RPC 2 state (4 + address when on WiFi, else 2), 3 device info (name, version, chip, host name), 4 scan (one result per network, strongest first, max 20, then an empty one; a new card switches STA on first; when the scan fails because a saved network is being retried, auto-reconnect pauses, it disconnects, scans, rejoins), 1 WiFi settings (joins for up to 20 s showing "Joining WiFi" on the panel; good = save to NVS, answer the address, restart; bad = error 3, back to before). `docs/install.html`: after flashing it reopens the port and asks; "Set up WiFi only" does the same for a card already running our software (no button, panel can stay connected). The page keeps answers that arrive before it waits for them (the scan comes as one burst). Card side tested on card 1 over COM10 with a PowerShell script (info, state, 16-network scan, checksums ok).
- **Packs** (0.9.6): pictures live in the private repo hogfanboy/pocket-jumbotron-content (not browsable on GitHub); CI checks it out with a read-only deploy key and `tools/build-packs.mjs private-content` → `docs/packs/` (public website, plain files). `content/` in this repo stays empty. Family codes / encrypted vault removed in 0.9.6. `cards` in pack.json limits a pack to named screens. CI runs on push and hourly (GitHub often skips the hourly run; Actions > Run workflow forces one). The builder is forgiving: any folder/file names (made web-safe), natural name order (no numbering), pack.json as JSON or `title: ...` lines, a broken pack is skipped with a warning.
- **WiFi setup hotspot**: hold S1 for 2 s → AP `PocketJumbo-XXXX` + a per-card 8-digit password shown on the panel → the captive pop-up page (`web/wifi.html`) lists networks → save → restart onto home WiFi. Leaving the hotspot always restarts the card.
- **S1 short press** shows the address screen for 10 s (also 10 s after WiFi connects): a white QR code of `http://<ip>` + the IP; a second press closes it. The panel switches to **fast scan** (2-bit color, ~650 Hz instead of 84 Hz) while it is up; that is what made phone cameras (Pixel camera app) read it (0.8.4). The screen switches every 2.5 s between a big code (2 LEDs per module, half brightness: phones read it from ~4-7 ft) and a small one (1 LED per module, quarter brightness: ~1.5-4 ft). Brightness made no difference to the distance (QR probe, 1.0.0-beta9).
- **OTA update + rollback**: `rollback.cpp` makes new firmware unconfirmed until `markAppValid()` runs after panel + storage start OK. 1 MB OTA takes ~12 s.
- **Self-update** (0.9.8, `online.ino`): daily at 3:xx local (minute = MAC byte % 50) the card reads `firmware/info.json` over HTTPS; a newer version (`verNum`: x.y.z, a `-betaN` sorts before its release) is streamed into the other app slot, SHA-256 checked against info.json, then restart (rollback still protects). Panel shows "UPDATING TO x.y.z" + progress. NVS `aupd` (default on), page switch "Update by itself"; `POST /api/update-site` = do it now. Tested on card 1: 0.9.0-labelled build -> 0.9.8 in 16 s.
- **HTTPS from the card** (0.9.7): `siteGet()` trusts ISRG Root X1/X2 (`site_ca.h`), needs the clock, frees the player buffers during the TLS fetch (heap ~150 KB then, ~78 KB while playing). ~0.8 s per fetch.
- **Stocks** (0.9.7): CI `tools/build-feeds.mjs` writes `docs/feeds/` hourly (`markets.txt` from Yahoo's chart API, 21 symbols with a day sparkline). Show item `stocks <sym,sym>` (price, change, day line). Feed cached 20 min on the card. The news ticker was removed in 1.0.0-beta3 (headlines too vague for this screen); old `news` lines are skipped.
- **Location** (0.9.7): ip-api.com (http) once per start: time zone when the page never set one, and `weather ... A auto auto` = weather where the screen is.
- **Jumbo font** (0.9.8): our own rounded-square font, stroke glyphs in `web/pjfont.js`, rendered with crisp edges (1.0.0-beta3: a pixel lights when a stroke covers ≥42% of it; `SOFT` in pjfont.js can bring 4-bit soft edges back per size, e.g. the huge font) into `pj_font.h` by `tools/make-pjfont.mjs` and by the page with the same code (same pixels). Font numbers 8 thin (cap 9), 9 small (11), 10 medium (16), 11 big (24), 12 huge (34); items using them also get thin Jumbo labels. Char 127 = degree sign.
- **Weather icons** (1.0.0-beta4): shaded drawings from `tools/make-wxicons.mjs` (gradient sun with 8 tapered turning rays, shaded crescent moon with craters, top-lit clouds with a darker underside, bolt) rendered with hard outer edges: color is supersampled, but a pixel is fully on (>=50% covered) or off; no glow. (beta3 flat icons were judged too plain.) Rain = solid 2 px blue drops, snow = solid white plus. Sprites (`wx_icons.h`, RGB565 + alpha; `web/wxicons.js` PNG for the page); rain, snow, stars, drift and lightning animated on the card.
- **Pack convert settings** (1.0.0-beta4): pack.json `format` ("gif" | "full", else auto) is the pack default and `pictures` { "<repo file name>": { fit: fill|fit, format: gif|full } } overrides per picture; the builder sets them (new packs start at gif) and keeps keys in step on reorder/delete; build-packs.mjs publishes them as manifest `format` and `pics` (keyed by the web-safe name); the phone page's addFile takes { fit, format } so it converts exactly as the builder previewed.
- **First show of a new card** (what the website installer puts on a card coming from Huidu; `tools/build-install.mjs`): clock, weather + forecast, the loose pictures in the content repo root, then every pack whose pack.json has `"install": true` (pack list order, then play order). Per picture in `pictures`: `"install": false` leaves it off new cards, `"dates": "MMDD-MMDD"` becomes `@dates=` (shown only between those days). 128x64 GIFs go on unchanged, anything else goes through make-gifs.mjs; files get numbered names (`04-01-merry-christmas.gif`). The holiday greetings are a normal pack, `Holiday Starter` in the content repo (made once by make-starter.mjs; id holiday-starter, order 90, install, greetings dated 1115-0106, color test off new cards). No install pictures at all = the generated greetings (local builds). `--first-show-only` lists the first show without compiling. The pack builder sets all of this ("On new cards" per pack, On/Off + dates per picture) and lists what a new card gets with the size against 4.1 MB (converted sizes once a pack has been opened).
- **Pack builder** (1.0.0-beta3, `tools/pack-builder.mjs` + `pack-builder.html`, launch config `pack-builder`, http://localhost:8095, this PC only): lists the content repo's packs, new pack, title/about/screens/order saved as real JSON, drop pictures in (web-safe names), drag to reorder (renames to 01-, 02-...), delete, each picture previewed exactly as a phone converts it (GIF/full color, size on a screen, pack total vs 4.3 MB). Publish = `git add -A`, commit, push the content repo, then `gh workflow run` so the website rebuilds right away. **Hosted copy** (1.0.0-beta4): the same page at `/builder/` on the website (docs/builder/, written by build-web.mjs, not committed). It picks its backend by address (localhost:8095 = local server, else GitHub): sign-in with a fine-grained token (Contents read/write on pocket-jumbotron-content, Actions read/write on hd-wf2-christmas-card) stored in localStorage (or sessionStorage when "Remember" is off); reads the tree + blobs, keeps edits in the page (renames reuse blob shas), Publish = blobs + a complete tree (current GitHub tree with the page's changes applied, no base_tree: deleting a path that's gone gives 422 GitRPC::BadObjectState) + commit (author = `<id>+<login>@users.noreply.github.com`) + ref update, then workflow_dispatch of build-and-publish.yml.
- **Online installer**: CI builds the firmware and `docs/install.html` (browser USB flasher) on every push to main.
- **CI checks** (1.0.0-beta7, `tools/test.mjs`, runs right after build-web, so a failure stops the run before anything is published): every inline script of the app, builder, installer, home page, go page and wifi page parses (modules via `node --check`); the page's effect list equals the firmware's `FX_NAMES`; FW_VERSION is x.y.z[-betaN]; page `newer()` and the card's `verNum` agree on order (release > its betas, beta10 > beta9).
- **Storage meter**: the page shows a bar and "1.2 MB of 4.3 MB space" above Send, and disables Send when the show doesn't fit.

## Hardware facts (confirmed)
- HUB75 pins: R1 2, G1 6, B1 10, R2 3, G2 7, B2 11, A 39, B 38, C 37, D 36, E 21, LAT 33, OE 35, CLK 34.
- **S1 = GPIO 17, active LOW.** S1 is *not* the boot/GPIO0 button.
- Flash is DIO, 8 MB, unencrypted.
- Card 1: MAC e8:06:90:fe:ee:d0 → `PocketJumbo-EED0`, FM6124C panel. Card 2: MAC e8:06:90:fd:5d:f8 → `PocketJumbo-5DF8`, RUL6024 panel. Spare WF2 (no panel): MAC e8:06:90:fd:ad:04, still on Huidu.
- **Most of the user's 15 cards have RUL6024 panels.** Panel chips differ between cards; the firmware handles both the same way.
- Huidu backups: card 1 `firmware-backup/wf2_backup_20261117_163902.bin` (sha256 `b7893e09…f45973ec`), spare `wf2_backup_20261118_002618.bin` (same Huidu apps, WF2_2 Jun 2024). Card 2's Huidu firmware was never backed up; card 1's backup on card 2 boots but stays blank (wrong screen settings, which LedArt can't change).
- Huidu layout was 2x 1 MB app + 5 MB media. Ours (`partitions.csv`): nvs, otadata, app0 1.75 MB, app1 1.75 MB, LittleFS 4.375 MB @0x390000, coredump. The app is ~1.2 MB (fw 0.7.x).

## Panel driver setup (fw 0.6.2, same on every card)
- The RUL6024 is a plain shift-register driver (not S-PWM) that needs **LAT high for 3 clocks** to latch (Huidu calls it "ICN2038S"; HUB75 DMA library discussion #525). The library's `cfg.driver = HUB75_I2S_CFG::DP3246` does that. The FM6124C works with the same setting.
- After `begin()`: set CLK back to the original edge with `GPIO.func_out_sel_cfg[clk].inv_sel = 0`. DP3246 init forces `clkphase = true`, which shifted the RUL6024 image 1 column left and misaligned the FM6124C halves.
- `panelRegInit()` writes config registers by bit-banging (pins borrowed from the LCD peripheral via `GPIO.func_out_sel_cfg`, then restored), LAT high for the last N of 128 clocks:
  - LAT 12 = REG1, LAT 13 = REG2 with the library's FM6126A values (smoother RUL6024 grays).
  - LAT 11 = all ones (RUL6024 brightness; it was much dimmer before).
  - LAT 14 = 0x0100 (removes RUL6024 noise in the lower middle-right with a good gradient; 0x0F00/0xFFFF also remove it but roughen the gradient; 0x0200/0x0400/0x0800 make it worse).
  - The FM6124C ignores all of them.
- Registers survive an ESP restart, so compare register variants only after a panel power-cycle (one variant per power-up).
- Refresh: keep the default `min_refresh_rate` 60. 30 gives smoother gradients but whites jitter; 45 still jitters. Dark grays are a bit weak at the very dark end.
- Probe sketches for this work: `firmware/probes/` (`clk_edge_test`, `fm_reg_variants`, `rul_bright_probe`, `rul_cmd_sweep`, `rul_reg_variants`, `rul_reg14_bits`).

## Decisions
- **Version 1.0** (from 1.0.0-beta1): the user is keeping this firmware; no going back to Huidu, so no Huidu backup step in the installer.
- **No PIN on the card page**: it goes to 15-20 family members; someone on the home WiFi can change the show. But other websites can't (1.0.0-beta6, `web.ino fromOwnPage()`): a POST with an Origin header must come from the card's own address, and the Host must be an IP or the card's name (stops DNS rebinding); otherwise 403. curl/node send no Origin and still work. Upload data handlers check it too, before writing anything.
- Toolchain: **arduino-cli** (no Python on this PC), ESP32 core 3.3.13, HUB75-DMA 3.1.0, AnimatedGIF 2.2.0. Node tools in `tools/` (sharp, gifenc, omggif).
- **One firmware and one panel setup for every card**: no per-chip detection.
- **The card stores GIF or JPEG frames, never WEBP**: no small WEBP decoder for the ESP32 and not enough RAM. WEBP is an input format, converted on the phone/PC.
- **Pictures are unlisted, not secret**: GitHub Pages is always public, so anyone who finds a pack's address can download it; keeping the source in the private repo only hides it from people browsing GitHub.
- **Pictures over home WiFi only**, not over the card's hotspot (see gotchas). The hotspot is just for entering WiFi details.
- **Send replaces everything** on the card (wipe, then write), so storage can't fill up.
- Stored format is 128x64 GIF. Each frame has 254 quantized colors + exact black + 1 transparent slot, and only pixels that changed are stored. The converter trims plain borders and fills letterbox bars with the image's own edge color when the edge is plain, otherwise black.

## Gotchas (learned the hard way)
- **Fast scan colors**: the HUB75 library builds its color table for 8-bit at compile time; restarted at 2-bit it uses only the table's 2 lowest bits, so most colors come out wrong (white looked green). Use `CF()` (channel 0 or 224). The library also never frees its GDMA channel on delete; `panelStop()` frees it.
- **An https page can't talk to the card** (mixed content; a bridge tab and Chrome's local-network fetch both failed in testing). An http page loading https code works, hence the starter page.
- **First flash of a Huidu card**: the USB port exists only briefly at power-up (Huidu then switches USB to host mode), or for as long as S1 is held. A watcher must be running *before* plugging in. `esptool --before usb-reset` then forces ROM download mode (`tools/backup-watch.ps1`, `tools/flash-watch.ps1`). With our firmware on, USB stays up, so no trick is needed.
- Flashing over PC USB can drop mid-write (the PC port also powers the lit panel). A retry works.
- ⚠️ VBUS back-feed not checked yet: until it is, unplug the card's own supply while it's on a PC's USB port.
- **Android vs. the card's hotspot**: a WiFi network without internet is "limited"/"sign-in". Only the sign-in pop-up may use it (and it has no file picker), and Chrome is routed over mobile data and times out, even with mobile data off. That's why uploads go over home WiFi.
- **Memory**: no PSRAM. Double-buffered DMA costs ~100 KB; with it, home WiFi + playing left only ~20-25 KB free. Now single-buffered (`USE_DOUBLE_BUFFER`): ~79 KB free with WiFi + playing. The player buffers are heap-allocated so the hotspot can free them (`playerFree()`). Turning WiFi off/on again in one session fails on this core, so restart instead.
- **Upload speed**: don't call `LittleFS.usedBytes()` (walks the whole FS) per chunk; measure once per file. 2.36 MB / 22 files takes 41 s.
- **Android 16+ Chrome needs the "Nearby devices" (local network) permission** to open the card page; without it Chrome says "site can't be reached" and offers a pop-up that opens Chrome's App info. Verified on the Pixel 10a.
- The card page is plain http: no WebCrypto, no geolocation, no camera APIs there. Fetching https files from GitHub Pages works (CORS allowed).
- **Heap is fragmented**: with WiFi up, ~80 KB free but the largest block is only ~31 KB. Allocate what's needed, not fixed big buffers (`.pjm` sizes its JPEG buffer to the file's biggest frame).
- **Build size check**: compile with `--build-property upload.maximum_size=1835008`; the default 1.25 MB check fails the build and leaves the old `.bin` in place.
- The Arduino prototype generator puts function prototypes before other files' includes: don't use library types (e.g. `esp_qrcode_handle_t`) or structs declared there in function signatures of non-main .ino files (declare such structs in the main .ino).
- The HUB75 library already applies CIE1931 correction, so don't add gamma (gamma 2.2 made everything too dark).
- GIF playback: apply the *previous* frame's disposal before the next frame, and clear the canvas when a loop restarts.
- Cameras show partial-frame bands at low refresh (rolling shutter, invisible to the eye).
- arduino-cli shares the user's Arduino IDE sketchbook/core (`~/Documents/Arduino/libraries`). Installs affect their other projects.
- Arduino `.ino` files are concatenated. Globals used across files must be declared in the main `.ino` before use. A C-linkage override (`verifyRollbackLater`) must live in a `.cpp` file.
